# Proto descriptions that render as paragraphs

The API documentation (`make build_docs`, published by `Generate API Documentation`) is generated by
protoc-gen-doc. Its HTML template renders two kinds of comments differently:

| Comment of a … | Rendered with | A newline in the comment becomes |
| --- | --- | --- |
| file (above `syntax`), service, message, enum | `{{p .Description}}` | a new paragraph |
| field, enum value, rpc method | `{{.Description}}` (raw HTML) | a space |

So a file, service, message or enum description keeps **one paragraph per source line**, with an empty `//`
line between paragraphs, and carries no `<p>` tags (the filter adds them; nested `<p>` renders empty
paragraphs). Inside `<pre>` a line break is written `&#10;`, which the filter does not split on and the
browser renders as a newline. Field, enum-value and method comments keep the usual line wrapping and may use
`<p>`, `<pre>` and lists as raw HTML.

- `make doc_rendering_check` fails when a p-rendered description wraps a paragraph across lines (it runs in
  the `Proto field presence` workflow and before `make release`).
- `make doc_rendering_fix` reflows them in place; it changes comments only.
- Both cover `ondewo/vtsi/*.proto` ONLY. The vendored `nlu`, `qa`, `s2t`, `t2s` and `sip` copies stay byte-identical
  to the upstream release they were copied from (`make vendored_protos_check`, run by `make release`): every client
  generates its vendored modules from them, and ondewo-vtsi's `test_vendored_protos_lockstep.py` compares those
  byte for byte with the service clients' own. 9.6.0 reflowed them (comments only) and that guard failed against
  the released `ondewo-vtsi-client` 9.6.0; 9.6.1 re-vendors them verbatim. A wrapped description in a vendored
  copy is fixed upstream, in its API repository, never here.
